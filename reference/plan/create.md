요구사항 또는 이슈사항을 대화를 통해 충분히 파악한 뒤 작업계획서(.md)를 생성해주세요.

$ARGUMENTS 내용이 있으면 출발점으로 활용합니다.

## 0단계: 입력 성숙도 분기
$ARGUMENTS를 확인하고 진입 경로를 결정해주세요:

### A. 아이디어 정리서 입력 (빠른 경로)
$ARGUMENTS가 `docs/proposals/idea-*.proposal.md` 경로이거나 정리서를 가리키면:
1. **1단계 인터뷰를 생략**하세요 — 문제·대상·가치·MVP 범위는 정리서에서 이미 확정되었습니다
2. 정리서 내용을 요구사항으로 채택하고, 핵심을 3~5줄로 요약해 사용자에게 확인받으세요
3. 정리서의 **"미해결 질문" 섹션 항목만** 질의하세요
   - 각 질문은 가능하면 **AskUserQuestion 선택지**(제가 2~3개 답안 제안)로 묻고, 서술이 필요한 것만 자연어로 질문
4. **"다기준 평가 (MCDA)" 섹션이 있으면** 쟁점·보완 제안을 작업계획서의 `리스크 & 고려사항`에 반영하세요
5. 미해결 질문이 모두 해소되면 바로 2단계로 진행하세요
6. 생성하는 작업계획서의 `개요`에 출처 정리서 경로를 명시하세요 (추적성)

### B. 자연어/입력 없음 (기존 경로)
아래 1단계 인터뷰를 그대로 진행하세요.

## 1단계: 요구사항 수집 (대화)
작업계획서를 바로 작성하지 마세요. 먼저 다음 관점에서 질의응답을 진행해주세요.
한 번에 많은 질문을 하지 말고, 답변에 따라 자연스럽게 이어가세요.

### 필수 파악 사항
순서대로 하나씩 자연어로 질문하며 파악해주세요:

1. **무엇을**: 어떤 기능/수정/개선이 필요한가?
2. **왜**: 이 작업이 필요한 배경은? (버그? 신규 기능? 성능? 고객 요청?)
3. **어디에**: 어떤 시스템/모듈/화면에 영향이 있는가?
4. **제약 조건**: 기한, 기술적 제약, 호환성 요구사항이 있는가?
5. **기대 결과**: 완료 후 어떤 상태가 되어야 하는가?

### 선택 파악 사항 (필요 시)
답변 내용에 따라 추가로 질문해주세요:
- 기존에 시도했던 접근 방식이 있는가?
- 관련된 다른 이슈/태스크가 있는가?
- 특별히 고려해야 할 엣지 케이스가 있는가?
- 참고할 문서, URL, 스크린샷이 있는가?
- 우선순위나 긴급도는 어떤가?

### 대화 규칙
- 답변이 모호하면 구체적으로 되물어주세요
- 기술적 판단이 필요한 부분은 코드베이스를 먼저 확인하고 질문해주세요
  예: "현재 auth 모듈을 확인해보니 JWT 기반인데, 세션 방식으로 바꾸려는 건가요?"
- 충분히 파악되었다고 판단되면 사용자에게 확인해주세요:
  "요구사항이 충분히 정리된 것 같습니다. 작업계획서를 작성해도 될까요?"

## 2단계: 작업계획서 생성
사용자가 작성 승인을 하면 아래 구조로 작업계획서를 생성해주세요.

### 작업계획서 구조
```
# 작업계획서: {제목}

## 개요
- 작업 배경 및 목적
- 요청자 / 요청일
- 예상 완료일

## 요구사항 분석
- 핵심 요구사항 정리 (대화에서 파악한 내용 기반)
- 제약 조건 및 전제 조건

## 작업 범위
- 포함 범위 (In Scope)
- 제외 범위 (Out of Scope)

## 기술 설계
- 아키텍처 변경사항
- 수정 대상 파일/모듈
- 의존성 및 영향 범위

## 작업 단계
1. 단계별 작업 내용
2. 각 단계의 예상 소요 시간
3. 선후 관계 및 병렬 가능 여부

## 리스크 & 고려사항
- 잠재적 리스크
- 대응 방안

## 검토 체크리스트
- [ ] 기존 코드 영향도 확인
- [ ] 문서 업데이트 필요 여부
- [ ] 테스트 계획
- [ ] 배포 계획

## TODO
<!-- 검토 단계에서 에이전트가 추가할 영역 -->
```

### 생성 절차
1. 대화에서 수집한 요구사항을 정리해주세요
2. 현재 프로젝트의 코드베이스를 분석해주세요:
   - 프로젝트 구조 파악
   - 관련 파일/모듈 식별
   - 기존 코드와의 연관성 분석
3. 위 구조에 맞춰 작업계획서를 작성해주세요
4. 작업계획서를 프로젝트 루트의 `docs/plans/` 디렉토리에 저장해주세요
   - 파일명: `plan-YYYYMMDD-간단설명.md`
   - 예시: `plan-20260401-로그인-API-리팩토링.md`
5. 생성 완료 후 파일 경로와 요약을 알려주세요:
   ```
   📋 작업계획서 생성 완료
   📄 파일: docs/plans/plan-20260401-로그인-API-리팩토링.md
   📌 제목: 로그인 API 리팩토링
   ```

## 후속: 다기준 평가 자동 실행 판단
생성 완료를 보고한 뒤, 아래 조건으로 평가 실행 여부를 판단해주세요.
**자동 실행 조건에 해당하면 사용자에게 묻지 말고 즉시 `/plan:evaluate {계획서 경로}` 절차를 이어서 실행**하세요.

### 자동 실행 조건 (하나라도 해당하면 실행)
- 평가 이력이 없는 **신규 기능**이며, 진행 여부가 아직 의사결정 대상인 경우
- 평가 이력은 있으나(0단계 A경로), 계획서 작성 과정에서 **범위·접근이 정리서와 크게 달라졌거나** 이전 판정이 🟡(보완 후 진행)였던 경우 → 재평가(N차)

### 실행하지 않는 조건
- 버그 수정·소규모 작업 (진행 여부가 자명 — 평가 비용이 의사결정 가치보다 큼)
- 이미 결정·확정된 요구사항 (고객 요청 등 진행이 확정 — go/no-go 게이트가 무의미)
- 🟢 판정 정리서 기반 + 범위 변화 없음 (재평가는 같은 답에 비용만 추가)

판단이 애매하면 AskUserQuestion으로 1회만 확인해주세요.

### 평가를 실행하지 않는 경우의 후속
**사용자에게 묻지 말고 `▶ 자동 진행: /plan:review` 한 줄 보고 후 즉시 `/plan:review {생성된 파일 경로}` 절차를 이어서 실행**하세요.
