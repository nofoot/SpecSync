# SpecSync 공통 규칙

`/spec`과 `/execute`가 함께 따르는 규칙이다.

## 커맨드 역할

| 커맨드 | 담당 status | 하는 일 |
|---|---|---|
| `/spec` | (새 Spec), draft, approved | 아이디어 → 생성 → 질문 해소·요구사항 승인 → 설계·Sub-task 작성·계획 검토 → planned. Spec 수정, principles 설정 변경, 현황 조회 |
| `/execute` | planned, in-progress, in-review | Sub-task 구현 → 리뷰 → done |

상대 커맨드의 담당 status인 Spec을 받으면 처리하지 않고, 그 커맨드로 실행하라고 한 줄로 안내한다(예: "SS-12는 planned 상태입니다. `/execute SS-12`로 실행하세요.").

## 경로

단계 문서 안의 `<이름>.md`는 SKILL.md `## 경로`의 단계 문서 폴더(`shared/stages/`) 기준, `templates/…`는 공용 폴더(`shared/`) 기준 상대 경로다. 사용자 프로젝트 기준으로 해석하지 않는다. 반면 `.specs/…`, `spec.md`, `design.md`, `subtasks.md`는 사용자 프로젝트의 파일이다.

## 진행 규칙

- 자동 전이는 이어서 진행하되, **사람 게이트(→approved, →planned, →done)에서는 반드시 멈추고 AskUserQuestion으로 확인받는다.** 사용자가 명시적으로 승인하지 않으면 상태를 바꾸지 않는다.
- 게이트 검사는 `gates.md`의 규칙을 따른다. 검사에 실패하면 실패 항목을 보여주고 해결을 돕는다.
- **의사결정성 변경은 자동 반영하지 않는다.** 범위 축소·확대, 기능 제거, 방향 전환, 목표·비목표 변경, REQ/AC의 의미 변경은 검토 의견이나 구현 중 발견에서 나왔더라도 AskUserQuestion으로 하나씩 결정받은 뒤 반영한다. 표현 보완, 누락된 리스크·테스트·Sub-task 추가처럼 사용자 의도를 바꾸지 않는 보완만 자동 반영한다.
- 상태를 바꿀 때마다 `spec.md`의 frontmatter `status`를 갱신한다. 승인 시 `approved_at`에 날짜를 기록한다. 사람 게이트를 통과하거나 상태를 되돌릴 때는 `## 변경 이력`에 `[승인]`·`[되돌림]`을 함께 기록한다(`## 거버넌스`). 요구사항이나 설계가 바뀌면 `spec.md`의 `## 변경 이력`에 한 줄을 추가한다.
- 템플릿에 없는 섹션에 기록해야 하면 섹션을 추가한다.
- 응답 끝에는 현재 상태와 다음에 실행할 커맨드(`/spec <KEY>` 또는 `/execute <KEY>`)를 한 줄로 알려준다.

## 거버넌스

규칙이 지켜졌는지 나중에 확인할 수 있도록 승인, 되돌림, 예외를 기록으로 남긴다.

### 이력 태그

`spec.md`의 `## 변경 이력`에 `- <날짜> [태그] 내용` 형식으로 추가한다. 태그가 없는 줄은 일반 변경 기록이다.

| 태그 | 언제 | 내용 |
|---|---|---|
| `[승인] <이전>→<이후>` | 사람 게이트에서 승인받아 상태를 바꿀 때 | 승인 대상 요약(→approved: REQ·AC 수, →planned: Sub-task 수, →done: AC 충족 수). 예외가 있었으면 `예외: <항목>` |
| `[되돌림] <이전>→<이후>` | 상태를 앞 단계로 되돌릴 때(요구사항 변경으로 draft, 리뷰에서 in-progress, epic을 planned로) | 사유 |
| `[예외] <전이>` | 게이트 검사 항목을 예외로 건너뛸 때 | 건너뛴 항목과 사유 |

### 상태 기록 검사

대상 Spec이 정해진 뒤 처리하기 전에, 그리고 Spec 하나의 현황을 보여줄 때, 현재 status에 필요한 `[승인]` 기록이 있는지 확인한다. 전체 현황에서는 `status.md`의 거버넌스 주의 사항을 만들 때만 본문을 읽는다.

- approved 이후: `[승인] draft→approved` (가장 최근 `[되돌림] …→draft` 이후)
- planned 이후: `[승인] approved→planned` (같은 기준)
- done: `[승인] in-review→done` (가장 최근 `[되돌림]` 이후)

없으면 "기록 없는 상태 변경"으로 알리고 AskUserQuestion으로 고르게 한다.
- **게이트 다시 수행**: 기록이 없는 가장 앞 게이트의 이전 상태로 되돌리고 `[되돌림]`을 기록한다. 되돌린 status가 현재 커맨드의 담당이면 평소대로 진행하고, 아니면 멈추고 담당 커맨드(`/spec <KEY>` 또는 `/execute <KEY>`)를 안내한다. `done` Spec에는 이 선택지를 주지 않는다(done은 수정하지 않는다).
- **현재 상태 인정**: 사유를 받아 `[예외] 기록 없는 상태 변경`으로 기록한다. 이 규칙이 생기기 전에 만든 Spec은 이 경로로 한 번 정리한다.

### 게이트 예외

게이트 검사 실패 항목을 해결할 수 없거나 사용자가 건너뛰기를 원할 때만 예외를 제안한다.
- `gates.md`에서 `(예외 불가)`로 표시한 항목은 예외로 건너뛸 수 없다. 사람 게이트의 승인 자체도 예외 대상이 아니다.
- 예외는 항목마다 AskUserQuestion으로 확인하고 사유를 받는다. 사유 없이는 예외로 처리하지 않는다.
- `[예외]`를 기록하고, 이어지는 `[승인]` 줄에도 예외 항목을 적는다.

### principles 변경

`commit`, `plan_review`, `reviewers`, `impl_review`, `impl_reviewers`, `protected_paths`는 검토와 보호 범위를 정하는 설정이다.
- 사용자 요청 없이 `.specs/principles.md`를 수정하지 않는다. 변경 요청은 `/spec`이 처리하고, `/execute`에서 받으면 `/spec`으로 안내한다.
- 바꿔 달라는 요청을 받으면 이전 값과 바꿀 값을 보여주고 AskUserQuestion으로 확인받는다. 검토를 끄거나 보호 경로를 줄이는 변경은 사유도 받는다.
- 바꾼 뒤 `.specs/principles.md`의 `## 변경 이력`에 `- <날짜> <키>: <이전> → <이후> — <사유>`를 추가한다.
- `plan_review: off`나 `impl_review: off`이면 해당 검토를 생략할 때와 게이트 검사 결과를 보여줄 때 "검토 꺼짐(principles)"이라고 함께 알린다.
