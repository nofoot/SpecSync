# SpecSync 공통 규칙

`/spec`과 `/execute`가 함께 따르는 규칙이다.

## 커맨드 역할

| 커맨드 | 담당 status | 하는 일 |
|---|---|---|
| `/spec` | (새 Spec), draft, approved | 아이디어 → 생성 → 질문 해소·요구사항 승인 → 설계·Sub-task 작성·계획 검토 → planned. Spec 수정, principles 설정 변경, 현황 조회 |
| `/execute` | planned, in-progress, in-review | Sub-task 구현 → 리뷰 → done |

상대 커맨드의 담당 status인 Spec을 받으면 처리하지 않고, 그 커맨드로 실행하라고 한 줄로 안내한다(예: "SS-12는 planned 상태입니다. `/execute SS-12`로 실행하세요.").

## 경로

단계 문서 안의 `<이름>.md`는 SKILL.md `## 경로`의 단계 문서 폴더(`shared/stages/`) 기준, `templates/…`는 공용 폴더(`shared/`) 기준 상대 경로다. 사용자 프로젝트 기준으로 해석하지 않는다. 반면 `.specs/…`, `spec.md`, `design.md`, `subtasks.md`는 사용자 프로젝트의 파일이다.

## 진행 규칙

- 자동 전이는 이어서 진행하되, **사람 게이트(→approved, →planned, →done)에서는 반드시 멈추고 AskUserQuestion으로 확인받는다.** 사용자가 명시적으로 승인하지 않으면 상태를 바꾸지 않는다.
- 게이트 검사는 `gates.md`의 규칙을 따른다. 검사에 실패하면 실패 항목을 보여주고 해결을 돕는다.
- **의사결정성 변경은 자동 반영하지 않는다.** 범위 축소·확대, 기능 제거, 방향 전환, 목표·비목표 변경, REQ/AC의 의미 변경은 검토 의견이나 구현 중 발견에서 나왔더라도 AskUserQuestion으로 하나씩 결정받은 뒤 반영한다. 표현 보완, 누락된 리스크·테스트·Sub-task 추가처럼 사용자 의도를 바꾸지 않는 보완만 자동 반영한다.
- 상태를 바꿀 때마다 `spec.md`의 frontmatter `status`를 갱신한다. 승인 시 `approved_at`에 날짜를 기록한다. 사람 게이트를 통과하거나 상태를 되돌릴 때는 `## 변경 이력`에 `[승인]`·`[되돌림]`을 함께 기록한다(`## 거버넌스`). 요구사항이나 설계가 바뀌면 `spec.md`의 `## 변경 이력`에 한 줄을 추가한다.
- 템플릿에 없는 섹션에 기록해야 하면 섹션을 추가한다.
- 응답 끝에는 현재 상태와 다음에 실행할 커맨드(`/spec <KEY>` 또는 `/execute <KEY>`)를 한 줄로 알려준다.

## 데이터베이스

principles의 `db_access`가 정확히 `direct`일 때만 이 절을 적용하지 않는다. 값이 없거나 `manual`, 그 밖의 값(오타 포함)은 모두 `manual`로 본다.

- 에이전트는 DB에 직접 연결해 데이터를 조회·생성·수정·삭제하지 않는다. DB 클라이언트 CLI(`psql`, `mysql`, `sqlite3`, `mongosh`, `redis-cli` 등), ORM·프레임워크 콘솔, 마이그레이션 적용·롤백, 시드 실행, DB에 접속하는 임시 스크립트, DB를 다루는 MCP 도구가 모두 해당한다.
- 스키마와 데이터 구조는 코드, 마이그레이션 파일, 스키마 정의 파일에서 파악한다. 실제 데이터나 스키마 확인이 필요하면 조회 쿼리를 사용자에게 준다.
- 마이그레이션·쿼리 파일을 **작성**하는 것은 코드 변경이므로 허용한다. **적용과 실행**은 사용자가 한다.
- 자동 테스트, e2e, 앱·개발 서버 기동, DB에 닿을 수 있는 빌드 명령은 실행 전에 접속 대상(호스트, DB 이름)을 테스트 설정에서 확인한다. 접속 정보가 비밀 파일에만 있으면 읽지 말고 사용자에게 묻는다(`## 보안 정보`). 테스트 전용·인메모리·임시 컨테이너 DB일 때만 실행한다. 개발·운영 DB이거나 확인할 수 없으면 실행하지 않고, 해당 verify를 `manual:`로 바꿔 사용자에게 넘긴다(바꾼 사실을 Sub-task 구현 메모에 적는다).
- 서브에이전트(계획·구현 검토자 등)를 호출할 때도 이 절의 금지를 프롬프트에 함께 전달한다.
- 사용자가 공유한 조회 결과나 실행 결과는 기록할 때 행 수, 성공 여부, 상태 같은 요약만 남긴다. 원본 데이터, 개인정보, 비밀 값은 `.specs/`에 기록하지 않는다.

**쿼리 전달 절차**
1. 실행할 쿼리를 `.specs/<KEY>-<slug>/queries/<Sub-task 키 또는 용도>.sql`(SQL이 아니면 해당 언어의 확장자)에 저장한다. 파일 첫머리 주석에 목적, 대상 환경, 실행 순서, 되돌리는 방법을 적는다. 데이터를 바꾸는 쿼리는 트랜잭션으로 감싸고 영향 행을 미리 확인하는 조회 쿼리를 함께 둔다.
2. 쿼리를 응답에 코드 블록으로 보여주고 AskUserQuestion으로 결과를 받는다(실행 완료 / 결과 공유 / 나중에 실행 / 실행하지 않음). 조회 결과가 필요하면 사용자에게 결과를 붙여 달라고 한다.
3. 결과 요약을 해당 Sub-task 아래에 `> db: <날짜> <파일> — <결과 요약>`으로 기록한다.
   - **나중에 실행**: Sub-task를 `status: blocked`로 두고 `> blocked: DB 실행 대기 — <파일>`을 적는다. 이어서 할 일은 `implement.md` 2단계에서 처리한다.
   - **실행하지 않음**: Sub-task를 `status: blocked`로 두고 `> blocked: DB 실행 거부 — <사유>`를 적는다. 대안은 `implement.md` 2단계의 Spec 수정으로 정한다.
4. 쿼리로 표현할 수 없는 작업이면 사용자가 수행할 절차를 단계별로 적어 같은 방식으로 전달한다.

## 보안 정보

비밀 값(API 키, 토큰, 비밀번호, 인증서·개인 키, 접속 문자열)과 개인정보를 다룬다. 비밀 파일은 `.env`·`.env.*`(`.env.example` 같은 예시 파일 제외), `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `credentials*`, `secrets*`, `.npmrc`, `.pypirc`, `.netrc`, `.pgpass`, `*.tfvars`, `*.tfstate`, `kubeconfig`와 principles `secret_paths`에 지정한 경로다. 이 밖에 비밀 값을 담는 파일(예: `appsettings.*.json`, `config/secrets.yml`)은 `secret_paths`에 추가한다.

**에이전트가 지키는 것**
- 비밀 파일의 내용을 읽지 않는다. 설정 구조가 필요하면 예시 파일, 설정 로더 코드, 키 이름만 확인하거나 사용자에게 묻는다.
- 비밀 값과 실제 개인정보를 응답, `.specs/`(spec·design·Sub-task·쿼리 파일·`[예외]` 등 모든 기록), 커밋 메시지, 코드, 테스트 데이터, 서브에이전트 프롬프트에 넣지 않는다. 예시·테스트·쿼리 조건에는 가상 데이터나 자리표시자를 쓴다.
- 사용자가 비밀 값이나 개인정보를 붙여 넣었으면 그 값을 다시 출력하거나 기록하지 않는다. 비밀 값이면 노출됐으니 교체를 권한다.
- 서브에이전트를 호출할 때 "비밀 파일을 읽거나 비밀 값을 출력하지 말 것"을 프롬프트에 함께 전달한다.
- **유출 검사:** Sub-task를 done으로 바꾸기 전에, 커밋 정책과 관계없이 커밋될 변경 전체(스테이징, 작업 트리, 추적되지 않는 새 파일)와 커밋 메시지를 검사한다.
  1. 파일 이름을 먼저 본다(`git status --porcelain` 등). 비밀 파일이 있으면 내용을 열지 않고 경고한다.
  2. 그 밖의 변경 파일에서 비밀 값으로 보이는 문자열(키 형식, `password=`, 접속 문자열, 개인 키 헤더)과 실제 개인정보를 찾는다.
  3. 발견하면 커밋하지 않고 파일:줄만 보고한다. 값은 인용하지 않는다.

**노출 위험 경고와 보안 우선 제안**

명세·설계·구현·검토 중 아래 같은 노출 경로를 발견하거나 사용자가 그런 방식을 요청하면, 그대로 진행하지 않는다. 위험을 한 줄로 설명하고 보안 우선 대안을 먼저 제안한다.

| 노출 경로 | 보안 우선 대안 |
|---|---|
| 코드·설정·테스트에 비밀 값 하드코딩 | 환경변수나 시크릿 매니저에서 주입, 예시 파일에는 키 이름만 |
| 비밀 파일이 `.gitignore`에 없거나 커밋 대상 | `.gitignore` 추가, 예시 파일 분리 |
| 로그·에러 메시지·응답에 비밀 값이나 개인정보 출력 | 마스킹, 필드 제외, 로그 레벨 분리 |
| URL·쿼리 문자열·클라이언트 번들에 토큰이나 키 포함 | 헤더·서버 측 보관, 공개 가능한 키만 클라이언트에 |
| 외부 서비스·서드파티로 비밀 값이나 개인정보 전송 | 최소 필드만 전송, 토큰화, 전송 전 동의·계약 확인 |
| 넓은 권한의 키·계정 사용 | 최소 권한 키, 범위·만료 제한 |
| 이미 커밋되었거나 공유된 비밀 값 | 코드에서 지워도 히스토리와 사본에 남으므로 즉시 교체(rotate)를 권한다. 히스토리 정리는 사용자가 결정한다(에이전트가 히스토리를 다시 쓰지 않는다). 교체하지 않기로 하면 `[예외] 보안 — 노출 비밀 미교체`로 기록한다 |

- 대안을 따르지 않고 원래 방식으로 진행할지는 의사결정성 변경이다. AskUserQuestion으로 결정받고, 진행하기로 하면 `## 변경 이력`에 `[예외] 보안 — <노출 경로>, <사유>`를 기록한다. 기록에는 값을 쓰지 않는다.
- 설계 단계에서는 비밀 값·개인정보를 다루는 Spec이면 design.md `## 리스크`에 노출 경로와 대책을 적는다.

## 거버넌스

규칙이 지켜졌는지 나중에 확인할 수 있도록 승인, 되돌림, 예외를 기록으로 남긴다.

### 이력 태그

`spec.md`의 `## 변경 이력`에 `- <날짜> [태그] 내용` 형식으로 추가한다. 태그가 없는 줄은 일반 변경 기록이다.

| 태그 | 언제 | 내용 |
|---|---|---|
| `[승인] <이전>→<이후>` | 사람 게이트에서 승인받아 상태를 바꿀 때 | 승인 대상 요약(→approved: REQ·AC 수, →planned: Sub-task 수, →done: AC 충족 수). 예외가 있었으면 `예외: <항목>` |
| `[되돌림] <이전>→<이후>` | 상태를 앞 단계로 되돌릴 때(요구사항 변경으로 draft, 리뷰에서 in-progress, epic을 planned로) | 사유 |
| `[예외] <전이>` | 게이트 검사 항목을 예외로 건너뛸 때 | 건너뛴 항목과 사유 |
| `[예외] 보안` | 보안 우선 대안 대신 원래 방식으로 진행하기로 결정했을 때(`## 보안 정보`). 전이와 무관하다 | 노출 경로와 사유. 값은 쓰지 않는다 |

### 상태 기록 검사

대상 Spec이 정해진 뒤 처리하기 전에, 그리고 Spec 하나의 현황을 보여줄 때, 현재 status에 필요한 `[승인]` 기록이 있는지 확인한다. 전체 현황에서는 `status.md`의 거버넌스 주의 사항을 만들 때만 본문을 읽는다.

- approved 이후: `[승인] draft→approved` (가장 최근 `[되돌림] …→draft` 이후)
- planned 이후: `[승인] approved→planned` (같은 기준)
- done: `[승인] in-review→done` (가장 최근 `[되돌림]` 이후)

없으면 "기록 없는 상태 변경"으로 알리고 AskUserQuestion으로 고르게 한다.
- **게이트 다시 수행**: 기록이 없는 가장 앞 게이트의 이전 상태로 되돌리고 `[되돌림]`을 기록한다. 되돌린 status가 현재 커맨드의 담당이면 평소대로 진행하고, 아니면 멈추고 담당 커맨드(`/spec <KEY>` 또는 `/execute <KEY>`)를 안내한다. `done` Spec에는 이 선택지를 주지 않는다(done은 수정하지 않는다).
- **현재 상태 인정**: 사유를 받아 `[예외] 기록 없는 상태 변경`으로 기록한다. 이 규칙이 생기기 전에 만든 Spec은 이 경로로 한 번 정리한다.

### 게이트 예외

게이트 검사 실패 항목을 해결할 수 없거나 사용자가 건너뛰기를 원할 때만 예외를 제안한다.
- `gates.md`에서 `(예외 불가)`로 표시한 항목은 예외로 건너뛸 수 없다. 사람 게이트의 승인 자체도 예외 대상이 아니다.
- 예외는 항목마다 AskUserQuestion으로 확인하고 사유를 받는다. 사유 없이는 예외로 처리하지 않는다.
- `[예외]`를 기록하고, 이어지는 `[승인]` 줄에도 예외 항목을 적는다. 직전 `[승인]` 이후 생긴 `[예외] 보안`도 다음 `[승인]` 줄에 `보안 예외 n건`으로 함께 적는다.

### principles 변경

`commit`, `plan_review`, `reviewers`, `impl_review`, `impl_reviewers`, `protected_paths`, `db_access`, `secret_paths`는 검토와 보호 범위를 정하는 설정이다.
- 사용자 요청 없이 `.specs/principles.md`를 수정하지 않는다. 변경 요청은 `/spec`이 처리하고, `/execute`에서 받으면 `/spec`으로 안내한다.
- 바꿔 달라는 요청을 받으면 이전 값과 바꿀 값을 보여주고 AskUserQuestion으로 확인받는다. 검토를 끄거나, 보호 경로·`secret_paths`를 줄이거나, `db_access`를 direct로 바꾸는 변경은 사유도 받는다.
- 바꾼 뒤 `.specs/principles.md`의 `## 변경 이력`에 `- <날짜> <키>: <이전> → <이후> — <사유>`를 추가한다.
- `plan_review: off`나 `impl_review: off`이면 해당 검토를 생략할 때와 게이트 검사 결과를 보여줄 때 "검토 꺼짐(principles)"이라고 함께 알린다.
