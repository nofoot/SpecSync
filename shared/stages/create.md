# create: 새 Spec 생성

## 1. 타입 판별

| 타입 | 기준 |
|---|---|
| bug | 기존 동작이 잘못됨(오류, 예외, 기대와 다른 결과)을 설명 |
| task | 설계 판단 없이 끝나는 작은 변경(설정, 문구, 의존성 갱신 등). Sub-task 3개 이하 예상 |
| epic | 독립적으로 배포 가능한 기능 묶음이 둘 이상. Sub-task 15개 초과 예상 |
| story | 그 외 기능 추가·변경 |

판별 결과와 근거 한 줄을 사용자에게 보여준다. 애매하면 AskUserQuestion으로 확정한다. epic의 하위 Spec으로 생성하는 경우(`plan.md`에서 호출)는 판별 결과를 보여주기만 한다.

## 2. 파일 생성

1. 키: 생성 직전에 `.specs/` 폴더를 다시 확인해, 같은 접두어 키(이번 실행에서 만든 것 포함) 중 최대 번호 + 1.
2. 폴더: `.specs/<KEY>-<slug>/` (slug는 제목을 영문 kebab-case로 3~5단어).
3. `templates/spec.<type>.md`를 읽어 `spec.md`로 만들고 `{{key}}`, `{{title}}`, `{{date}}`, `{{parent}}`를 채운다. 부모가 없으면 `parent` 줄을 지운다.
4. 사용자 입력과 저장소 조사(관련 코드, 기존 동작)를 바탕으로 본문을 채운다.
   - 입력에 없는 내용을 지어내지 않는다. 판단이 필요한 부분은 `## 미해결 질문`에 `- [ ] Qn`으로 남긴다.
   - 모든 REQ에 AC를 1개 이상 쓴다. bug는 회귀 AC에 `[regression]` 태그를 붙인다(`- AC-1.1 [regression] Given …`).
   - 남은 자리표시자(`{{…}}`, `<전제>` 등)와 빈 placeholder(내용 없는 `- [ ] Q1`, 빈 `- 목표:`)를 모두 채우거나 지운다. 질문이 없으면 `## 미해결 질문` 아래를 "없음"으로 둔다.
   - 템플릿의 안내 주석(`<!-- -->`)은 채운 뒤 지운다.
   - 아이디어 단계를 거쳤으면 `## 검토한 대안`을 채운다(템플릿에 없으면 추가).
5. epic이면 하위 Spec 후보를 `## 하위 Spec` 표에 제목과 타입만 적는다(키는 plan 단계에서 생성).

## 3. 이어서

`plan.md`의 epic 하위 Spec 생성으로 호출된 경우는 여기서 끝낸다. 그 외에는 `clarify.md`를 이어서 수행한다.
